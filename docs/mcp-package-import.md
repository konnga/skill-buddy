# 从包导入 MCP

在 MCP Servers 页面右上角使用“从包导入”。发现结果是配置候选，选择后回填到
新建 MCP 表单；核对命令、参数和环境变量，再选择客户端并预览变更。

## 发现范围

- 当前可定位的 Node/npm 环境中的全局顶层包。
- npm 配置的缓存目录 `_npx` 中，用户请求过的顶层包；兼容旧版缓存的直接依赖记录。
- 已登记项目 `package.json` 声明且已安装的直接依赖，包括开发和可选依赖。
  向上查找安装目录，以支持依赖提升和包目录的符号链接。

扫描仅读取包元数据或调用 npm 查询目录，不运行包入口、不安装依赖、不查询远程
注册表。Node/npm 不可定位或某项查询失败时，继续检查可用缓存和项目，显示问题摘要。

## 候选识别与配置草稿

包必须有合法名称、版本及可用 `bin` 入口。`mcpName` 字段作为明确声明；包名、
关键词或明确的 MCP server 描述作为推断线索，推断候选标记为“待确认”。已知的
MCP SDK 和 Inspector 不作为服务器候选。

元数据不能完整描述服务器启动要求；多入口包需要用户选择真正的服务入口。
没有 `bin` 入口的包、Python/uvx 包和普通传递依赖不在本次自动发现范围内。

草稿使用固定版本的 `npx -y --package=<包名>@<版本> -- <入口>` 命令，避免将
`_npx/<缓存标识>` 的临时绝对路径保存为客户端启动命令。项目候选带项目工作目录。
用户可以在表单中修改命令，添加参数和环境变量。客户端首次启动时按 npm 的规则
复用已有包或获取依赖；SkillBuddy 的发现和配置写入阶段不下载包。

## 稳定性与资源限制

每次扫描运行于独立 Electron utility process，同时只允许一轮任务。主进程校验
消息大小和字段，重新构造候选定义，再用现有 MCP 定义校验器检查。

| 项目 | 单轮上限 |
|---|---|
| 已登记项目 | 32 |
| 检查包数量 | 1000 |
| 缓存环境数量 | 128 |
| 目录枚举及安装路径探测 | 4000 |
| 候选数量 | 100 |
| 问题记录 | 20 |
| 单份包元数据 | 128 KiB |
| 子进程消息 | 512 KiB |
| npm 路径查询 | 每项 3 秒 |
| 扫描时间 | 20 秒 |

扫描进程的 V8 堆上限为 128 MiB，npm 查询进程为 64 MiB，这不是进程总内存上限。结果分批返回并限制更新频率。
后台有独立的存活期限；进程异常退出、超时或消息格式错误只结束本次任务，保留
已发现结果。取消、关闭弹窗、切换页面或关闭窗口会停止任务并清理监听器。
取消发生在进程尚未启动完成时，启动完成后也会立即终止。

## 验证

针对性回归覆盖三种包来源、依赖提升、旧版 npx 缓存、重复缓存、无效入口、
损坏与超限文件、工作量限制、取消、进程异常、超时、超限/循环消息、启动失败、
窗口关闭，以及旧请求结果隔离。

测试使用临时目录，并将测试包的入口写成会抛错的脚本，验证发现阶段不执行入口。
